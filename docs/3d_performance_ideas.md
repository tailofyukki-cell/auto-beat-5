# 3D表示の軽量化アイデア

記録日: 2026-09-17

今後の検討用資料。今回の作業は資料の追加のみで、ゲームの変更や新しい性能測定は行っていない。
現在の3D表示はPygameによる疑似3D。以下の追加案は実測してから採否を決める。

## 守ること

- 通常表示と3D表示の判定・音楽時刻・入力処理を一致させる。
- 判定直前の見かけの加減速や跳ねを再発させない。
- ノーツ・判定ライン・同時押し線・HOLDの見やすさを優先する。
- スコア表示の華やかさはできるだけ維持する。
- マスコットの動きやコンボ別ポーズを今後増やせる余裕を作る。
- FPSの平均値だけでなく、一瞬の引っかかりと入力遅延を評価する。

## 現在確認できる対策

2026-09-17にsrc/app.pyを読み取り確認。個々の効果を今回再測定したものではない。

| 対策 | 実装箇所 | 目的 |
|---|---|---|
| レーン背景のキャッシュ | _playfield_base_cache | 静的なレーンの描き直しを減らす |
| エフェクト範囲だけの合成 | _blit_local_primitives | 全画面サイズの透明画像を扱う回数・面積を減らす |
| 表示対象ノーツの絞り込み | _note_draw_index、bisect | 画面外ノーツの描画処理を減らす |
| HUD文字のキャッシュ | _hud_text_cache | 同じ表示内容の文字生成を繰り返さない |
| 背景の合成結果をキャッシュ | _background_composite_cache | 背景の拡大縮小・暗幕合成を繰り返さない |
| マスコットの拡大縮小・変形結果を再利用 | mascot_scaled_cache、変形用LRUキャッシュ | 毎フレームの画像変形を減らす |

以前の開発記録では、数字を1桁ずつ画像化して並べる案は文字列全体のキャッシュより遅く、常用しない判断となっている。再検討する場合も比較測定を先に行う。

## 追加で試すアイデア（実施状況は末尾に追記）

| 優先度 | 案 | 期待する効果 | 注意点・妥協点 |
|---|---|---|---|
| 高 | 装飾レイヤーの更新頻度を下げる | 背景ビジュアライザーなどの計算・描画回数を減らす | ノーツ・入力・音楽時計は間引かない。装飾だけ30fps相当などを比較する |
| 高 | 発光だけ低解像度で描画する | 大きなぼかし・透明合成のピクセル処理を減らす | 最終拡大のコストも測る。文字・数字・ノーツ本体は鮮明に維持する |
| 高 | 素材を表示サイズに合わせて事前調整する | 大きすぎるPNGの展開メモリ・縮小処理を減らす | 元画像は保管し、配布用派生画像を作る。透明余白を削る場合は基準位置を記録する |
| 高 | コンボ別ポーズをプレイ前に読み込む | 50・100・200コンボで画像を差し替える瞬間の停止を防ぐ | 選択中キャラの必要分のみ。全10キャラ分を常駐させない |
| 中 | 発光やスパークの小画像を再利用する | 同じ形の生成・描画準備を減らす | 色・サイズ・透明度の組合せを制限し、キャッシュ肥大化を防ぐ |
| 中 | 同時に出す装飾の量に上限を設ける | HOLD・PERFECT・カットインが重なる場面の負荷を抑える | 判定情報を消さず、古い粒子や背景装飾から減らす |
| 中 | レーンの静的部分と動的部分をさらに分離する | 現状のレーンキャッシュ後に残るコピー・描画負荷を減らす | 背景の透過、解像度、レーン数の変更時に正しく更新する |
| 中 | 装飾用Surfaceの再利用を検討する | 毎フレームの確保・破棄を減らす | 消去処理の負荷と残像、共有Surfaceのalpha変更による副作用を確認する |
| 中 | 手動の描画品質設定を用意する | 低性能PCでも演出量を選んで遊べる | 軽量設定でもノーツの位置・速度・判定は一切変えない |
| 低 | 計測結果を基に描画バックエンドを再検討する | CPUによる合成が限界の場合の改善候補 | GPU化は大きな変更。移植・ドライバー差・入力遅延の検証が必要で、初版の必須作業にはしない |

## マスコット素材の準備

- 同じキャラのポーズ画像はキャンバス・足元・顔の基準位置をそろえる。
- 大きな原画とゲーム用画像を分け、ゲーム用は最大表示サイズを基準にする。
- クロスフェード中は2枚分の描画が必要なので、低性能PCでも測定する。
- ポーズ未用意の場合は前段階の画像を再利用し、毎フレーム代替画像を生成しない。
- コンボとポーズの対応は[マスコットのコンボ別ポーズ案](mascot_combo_pose_plan.md)を参照。

## 検証方法

1. 同じPC・曲・譜面・解像度・レーン数で変更前後を比較する。
2. 通常表示と3D表示の両方を測る。静かな場面だけでなく高密度・HOLD・コンボ演出の重なりも含める。
3. 1フレームの処理時間の中央値・95/99パーセンタイル・最大値、長い停止の回数、メモリを記録する。
4. 描画、画像変形、合成、画面への表示待ちを可能な範囲で分けて測る。FPS制限の待ち時間と処理負荷を混同しない。
5. 入力処理時間の計測と実プレイの感触を両方確認する。FPS改善だけで入力遅延が解消したと判断しない。
6. キャッシュが温まった後だけでなく、初回の演出・ポーズ切り替えも試す。
7. 一時停止・再開、Alt+Tab、HOLDと通常ノーツの同時操作を回帰確認する。

60fpsの1フレームは約16.7ms。これは時間予算の目安であり、達成済みの測定値ではない。
描画待ちの対策で音楽時計や入力ループを変える場合は、autobeat-input-regressionスキルに従って別途検証する。

## 2026-09-20: 背景ビジュアライザーの30Hz更新を実装

- `_draw_audio_visualizer`で、音楽時刻を30Hz単位に区切り、同じ区間の描画済み画像を再利用する。
- 通常表示・3D表示の背景に適用。波形の細かさ・色・透明度は維持する。
- ノーツ、スコア演出、マスコット、カットイン、入力、判定、音楽時計の更新頻度は変更しない。
- 時刻の巻き戻し、セッション、解析データ、解像度、レーン色が変わると描画し直す。一時停止で音楽時刻が止まれば同じ画像を使う。
- キャッシュは1枚のみ。RGBA画像は1280x720で約3.5MiB、1600x900で約5.5MiB。常駐メモリと引き換えに波形計算・Surface生成を減らす。
- 毎フレームの画像合成は残る。背景の動きが30fps相当になるため、実機で滑らかさを確認する。

### 簡易計測

開発PC、Python 3.13.11 / Pygame 2.6.1、SDL dummy、画面への表示待ちなし。
180フレームを60fps相当の時刻で3回ずつ処理し、背景生成と合成の平均時間を比較。
変更前相当は同じ描画関数を毎フレーム呼び出す。ゲーム全体・実入力遅延の測定ではない。

| 描画サイズ | 毎フレーム生成 | 30Hzで再利用 | 平均処理時間削減 |
|---|---|---|---|
| 1280x720 | 4.715ms | 3.521ms | 約25.3% |
| 1600x900 | 7.129ms | 4.565ms | 約36.0% |

測定には実行順や他プロセスによる変動を含む。全体FPSや他PCで同率の改善を保証しない。
全179テスト・7サブテスト成功。60フレームで生成30回、停止・巻き戻し、キャッシュ無効化、同一サンプル時刻での画素一致を確認。
実機での滑らかさ確認と配布EXE/ZIPの再ビルドは未実施。

## 2026-09-25: 発光低解像度化の試験と装飾上限

### 採用: 装飾の同時量を制限

- ヒット演出は各レーンの最新1件、全体最大7件。同じレーンの連打で古い発光を重ねない。7レーン同時押しの各レーンの反応は残す。
- HOLD粒子は全レーン合計21個以下。各レーンへ均等に割り振る（整数切り捨て）。通常表示は従来1レーン9個、3Dは5個を上限として維持する。
- 7レーンHOLD時は通常63個から21個、3D35個から21個になる。少ないHOLD数では元の密度を維持する。
- スコア、判定文字、ノーツ本体、HOLD本体、マスコット、音楽時計、入力処理は変更しない。
- 一律の全画面装飾予算ではなく、今回負荷が重なるヒット・HOLD粒子を対象とする。ゲーム全体の改善率は未測定。

### 不採用: 今回試した発光低解像度化

3DのPERFECTレーン発光のみ半解像度で描き、拡大画像をキャッシュする方式を試作した。
単純拡大では斜めの輪郭に段差が目立つため、滑らかな拡大も比較した。
開発PC・SDL dummy・1600x900・固定のレーン多角形1枚を反復描画した簡易計測では、滑らかな拡大とキャッシュの方式は平均0.480msから0.518msへ悪化した。初回は約1.05ms。
SDL2の透明合成も試したが、別の1000回比較では従来0.454msに対し0.710msとなった。
時間は発光単体の生成・合成で、実画面への表示待ちやゲーム全体のFPSではない。実行順・他プロセスによる変動を含む。

この試作は削除し、発光は元の解像度のまま維持した。低解像度化全般が無効という結論ではなく、複数発光を一括処理する方式などは将来の別検討とする。
試作中のartifacts/glow_preview画像は検証用で、採用版の画面ではない。

## 2026-09-25: 静的レーン前景と動的部分の分離を採用

- 従来キャッシュしていたレーン面・横線に加え、境界線、外枠の発光、判定台を静的前景として保持する。
- 動的なのは流れる光の筋と奥側の明るさ。ノーツ、入力、時計、判定は変更しない。
- 毎フレームのSurface.copyによる確保をやめ、作業用Surfaceを再利用する。背景の転送自体は必要。
- 静的前景は色キー付きRGBAコピーで配置する。通常のアルファ合成で重ね直すと元の透明度と変わるため、元のピクセル置換順序を維持する。
- サイズ・レーン数・レーン色・レーン位置が変わった時だけキャッシュを再生成する。各キャッシュは最新構成の1枚のみ。
- 作業用画像と静的前景の常駐メモリが増える。1600x900のRGBA2枚なら圧縮前で約11MiBが目安（従来の一時コピー分を含む）。

## 2026-09-26: 大きい装飾用Surfaceの再利用を採用

- `_blit_local_primitives`で32768ピクセル以上の一時Surfaceだけをサイズ別に再利用する。
- 小さい装飾は管理コストで遅くなるため従来どおり生成する。再利用画像は毎回透明色で全面消去し、残像・前回の色を残さない。
- 保持上限は32枚、合計8MiB。上限を超える場合は古い登録から削除し、単体で8MiBを超える画像は保持しない。
- 解像度や形状の異なる描画もサイズ別に扱う。ノーツの位置、描画順、透明度、入力・判定・時計は変更しない。

### 簡易計測

開発PC、Pygame 2.6.1 / Python 3.13.11、SDL dummy。
固定形状の局所描画2000回を5回測定した中央値（1呼び出しの平均時間）：

| 対象 | 変更前 | 常時再利用の試作 |
|---|---|---|
| 小さい装飾 | 0.0135ms | 0.0157ms（悪化のため対象外） |
| 大きいレーン発光 | 0.6284ms | 0.4494ms（約29%短縮） |

採用するサイズ制限付き方式で、1600x900・7レーンのPERFECT演出7件が全試行で生存することを確認しながら比較した。
180フレーム相当を3回測定したCPU時間の中央値は、旧3.993ms、新3.299ms（約17%短縮）。発光開始後0～29msの範囲を繰り返し、キャッシュは各試行前に空にしている。
この測定は描画呼び出し部分のみで、実表示待ちやゲーム全体のFPS・入力遅延の改善率ではない。端末や場面による変動がある。
`tests/test_decoration_pool.py`で画素一致・透明度変更・画面外の形状・再利用・上限を確認する。実機プレイとEXE/ZIPの再ビルドは未実施。

## 2026-09-27: 通常表示のHOLDスパーク画像を再利用

- 通常表示で繰り返し生成していたスパーク画像（白い円と色付きの輪）を、色・半径・透明度をキーに再利用する。
- 値を量子化せず、元の画素と描画順序を維持する。動く位置と粒子数は変更しない。
- 最大2048枚、最大18x18ピクセル。画素データは最大約2.53MiB、別途辞書・Surface管理領域が必要。上限では古い登録から削除する。
- レーン下部の広いHOLD発光は今回変更せず、スパークのみを対象にする。

### 比較結果

開発PC・SDL dummy・1600x900。通常表示のHOLD装飾描画全体を1200フレーム相当、3試行。キャッシュは各試行前に空にし、1呼び出し当たり平均時間の中央値を比較した。

| 1 | 0.0726ms | 0.0532ms |

約9～27%短縮。ただし絶対差は約0.02～0.04msで、ゲーム全体が大幅に速くなる変更ではない。

## 2026-09-27: 描画品質の手動設定

## 2026-09-28: 軽量設定のカットイン・顔アップ

- 軽量設定ではカットインの画像回転と連続ズームを省き、サイズ調整済み画像1枚を再利用。スライド・フェード・枠・文字は維持する。
- 専用カットイン画像とマスコット代用の両方に適用する。元画像をコピーして共有画像の透明度を変更せず、描画後はキャッシュ画像のalphaも255へ戻す。
- 顔アップは切り抜き・拡大・枠生成を30Hzまでに制限し、作成済みの吹き出し画像1枚を再利用する。画面上の位置は毎フレーム追従する。
- 新しいコンボ演出、マスコット変更、描画サイズ変更時は顔アップを更新する。
- 標準設定の回転・ズーム・顔アップ更新は従来どおり。ノーツ・判定・入力・通常のマスコット動作は変更しない。

### 検証

開発PC、SDL dummy、1600x900、実マスコット画像。顔アップとマスコット代用カットインを600フレーム相当（60Hz時刻）、3試行で比較。ファイル探索を除くため専用カットイン取得はNoneに固定、各試行の演出キャッシュは空から開始した。
1呼び出し当たり平均時間の中央値は、標準0.9763ms、軽量0.4117ms（約58%短縮）。これは両演出だけの処理時間で、ゲーム全体・実表示待ち・入力遅延の計測ではない。
全194テストと34サブテスト成功。顔アップの30Hz制限、イベント変更時の更新、標準への復帰、元画像の保護、軽量カットインの回転省略を確認。
比較画像はartifacts/combo_quality/standard-low.png（左:標準、右:軽量、演出部分だけの確認画像）。実機プレイと配布EXE/ZIPの再ビルドは未実施。

## 2026-09-28: 軽量設定のマスコット変形を30Hz化

- 軽量設定の常駐マスコットは、回転・拡大画像の取得更新を音楽時刻の30Hz区間ごとに行う。同じ区間は直前画像を再利用する。
- 上下移動・画面上の位置・一時停止時の透明度は毎フレーム更新する。ノーツ・入力・判定は変更しない。
